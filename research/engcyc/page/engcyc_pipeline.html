Each read shape is solved as a metasmith plan on the 0.25.0 standard library. Nothing has run yet.

  10. U10

    CLEAN lane, measured on fir with real ESM-1b and equal accuracy everywhere (DH10B F1 0.929-0.930). A 48-core CPU task (bf16, 6x8 pinned workers) is 1.2-1.6x slower than one 3g.40gb GPU slice in fp32 and 4.5-5.6x slower than the slice in bf16; a full 192-core node is 1.4-1.5x slower than a bf16 slice. In core-hours CPU costs 17-20x the fp32 GPU lane and 63-74x a bf16 GPU lane (COMEBin moved to CPU at 23x). Nothing below bf16 beats it, on CPU (int8, int4, ONNX int8) or on the GPU (fp8, int8 and int4 through torchao, eager or compiled; tested 2026-10-26): each is slower than bf16 or moves 2-12% of the kept EC sets on metagenome ORFs, against 0.75% for bf16. Engcyc after ORF centroid dedup: GPU bf16 on 1g.10gb slices about 115 slice-hours, or CPU about 30,000 core-hours (about 15 h on 2,000 cores). Which lane?

  11. U11

    Metabuli GTDB r232. Inodes are not the cost: a Metabuli index is about a dozen files (fir's GTDB 214.1 copy is 11 files, 101 GB), so r232 is about 12 files and 744 GB. A hybrid plan is not possible inside one run: a metasmith run drives one agent, and Nextflow needs one shared work dir. Hybrid works only as two runs with a seam: export every contig, classify on the Arbutus Metabuli service, import the calls as givens. Arbutus caps at 120 GB RAM, so it streams the index about 7 times per chunk, about 700 s per chunk, one job at a time (parallel workers contend for one Ceph stream). An estimated 360 Gbp of Engcyc contigs would be about 1,000 chunks, about 200 h serial. fir's 768 GB nodes hold the whole index, so a job needs one pass and jobs run in parallel. Recommended: download r232 once into /project/rpp-shallam (35 TiB free, out of reach of scratch purges), streaming the tarball through tar so the peak is 744 GB, not 1.4 TB, and run Metabuli on fir.

  12. U12

    Reuse rule (Tony: reuse where methods match, regenerate where they differ). Where a source never recorded its tool version (the = ? cells, mostly Spanish Lakes annotation), reuse it or regenerate it?

  13. U13

    CarveMe from the 4-lane calls (Tony: test it, report like E4 Fig 1). Two shapes. (a) Score CarveMe's own BiGG universe from the 4-lane calls: translate each ORF's MNXR or EC call to BiGG reactions and pass it as CarveMe's eggNOG-style input, so carving and gap fill stay stock. Needs an MNXR-to-BiGG crosswalk, and BiGG and MetaNetX 4.5 disagree on 1,231 of 2,751 reactions.   14. U14

    TreeSAPP, deferred (Tony 2026-10-22: maybe add later). TreeSAPP is a targeted tool, not a general annotator: it places only the genes of the families it has a reference package for (an HMM, a tree and a placement model each), so it answers questions about chosen marker genes and says nothing about the rest. Nothing in the library runs it. To add it later: pick the gene families the Engcyc questions need, take the curated packages for them (John already builds packages, e.g. the PR_22 rhodopsin package), write one transform for treesapp assign on the pipeline's ORFs, and time one sample on fir.

What solving the plan changed

  • GTDB-Tk and CarveMe now run on every quality MAG

    In 0.25.0 nothing per-genome reads the aggregator's pool, so GTDB-Tk and the GEM lane could only take one binner's bins. Two new transforms, gtdbtk_quality and prodigal_from_quality_bin, read the pool directly. Retyping the pool as a genome instead makes the solve cycle, because CheckM2 on the pool then satisfies the aggregator's own inputs.

  • iPHoP's tree is built from the MAGs it adds

    gtdbtk_de_novo took any genome set and settled on DAS Tool's bins, while iphop_add_to_db added the quality MAGs. The trees then do not describe the genomes being added. gtdbtk_de_novo_quality builds the tree from the quality pool, and DAS Tool leaves the plan.

  • Annotators read prodigal's whole-assembly ORFs

    prodigal-gv's ORFs on the viral frozen set also descend from the assembly, and the solver fed them to the GPR lanes and four annotators. prodigal-gv is out. Viral KOs are the assembly KOfam calls joined to vOTUs, and the driver fails any plan whose ORFs do not come from prodigal.

  • The de novo tree takes days

    GTDB-Tk de_novo_wf infers a FastTree over about 190,000 taxa, once per dataset, near fir's 7-day limit. Only iPHoP's MAG-augmented host database needs it. Running iPHoP against the stock Jun25_rw database removes it.

  • DIAMOND keeps 5 hits everywhere

    Tony standardised every Engcyc collection on 5 UniRef50 hits per ORF, which the contig LCA* vote needs. The GPR still reads the best hit. Results searched with 1 hit, including Cyanoverse's 99M ORFs, are imported under a legacy type, so the plan searches them again.

  • The MetaPathways stage is in the plan

    The metapathways session's transforms solve in every shape: ARAGORN tRNAs, barrnap rRNAs with GTDB taxonomy, a contig LCA* vote and PathoLogic PGDBs per assembly and per quality MAG. CarveMe 1.6.6 is now the library pin. On the SG8W14 pilot, PathoLogic took 3.7 GB and 30 min per assembly and about 2.5 min per MAG, and CarveMe 1.3 GB and about 11 min per MAG.

  • GTDB-Tk on the quality pool has its own type

    As a second producer of taxonomy::gtdbtk, gtdbtk_quality answered the per-binner GTDB-Tk targets of the shipped metagenomics_from_paired_reads template, which stopped solving. Its product is now taxonomy::gtdbtk_quality, and all 12 templates build.

  • No de novo hybrid lane

    OPERA-MS is only in E5's bench library. Every hybrid dataset already has an E5 assembly, so hybrids enter as the existing-assembly shape.
