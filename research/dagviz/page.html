E2 Plan, Three Ways

Benchmark arm E2 — nf‑core/mag's pipeline on CAMI, driven by metasmith — drawn through the modes of DagRenderer. The first panel is one arm's full plan and the switch moves it; the second is a single solve carrying both read shapes; the last is the tool inventory over both arms.

plain

The current style. Every node the plan builds, transforms and data alternating. E2 declares thirteen environments and a database as givens, so the first rows are resources before any read appears. This is the one panel that is a single run, so it is the one the arm switch moves.

one solve, both read shapes

1 short + 1 long sample 9 steps · 2 cases

A single plan carrying both arms, asked for one e2::comebin_bin. COMEBin names no assembler — it requires the generic e2::assembly and an e2::binning_bam descended from it — so both arms can reach it and the solver builds both chains at once. The short arm runs fastp → MEGAHIT → bowtie2, the long arm Porechop ABI → Chopper → Flye → minimap2, and comebin is instantiated once per arm on its own BAM. The tool environments are hidden here; they are givens standing outside every sample lineage, and thirteen of them at the top bury the shape.

One detached block per transform, in a grid of identical boxes. Each block is what the tool declares, not what a step bound it to — which is why four checkm2 steps reading four bin types are one block requiring e2::bin. Reading these

A triangle is a transform, a hollow circle a data instance, a filled circle a target. The transform carries the weight and the data recedes: a plan is a sequence of things done, and the types are what they are done to. The layout puts one node per row and routes edges down lanes to its left, so height counts nodes and width counts how many edges are in flight.

The legend marks no targets. A block is a signature rather than a run, and an output that happens to be a target of this plan is still just an output of the transform, so every output there draws the same.

Only the plain drawing is coloured, on the module scheme: a hue per dominator subtree. That says something across a whole plan and nothing inside a three-node legend block or a bare chain of steps, so the other two are monochrome.

A data node is one per slot, not one per type. A given draws once per type, because its instance ids are per-sample and a 208-sample plan would otherwise put 208 circles where the plan means one input. Everything a step makes draws once per instance, because that id is the slot — structural, one per branch, and the same whether the plan carries one sample or two hundred. Keying those by type name too is what used to draw the two arms' binning_bam as a single circle fed by both aligners and read by both binners, a join neither arm runs. It also collapsed the four checkm2 steps onto one output; they now have four, which is why the per-arm counts moved to 58 and 52.

What the one-solve panel does not extend to is the full E2 target set. Both arms reach COMEBin because it names no assembler. Ask for e2::megahit_assembly, or for the short-only FastQC and fastp reports, and one arm cannot fill the slot: the merge then substitutes Flye's product for MEGAHIT's and the plan witness catches it as emission. So the two full arms stay two solves — not because the read shapes cannot mix, but because that target set asks each case for something only the other can make.

fastqc_raw sits alone at the top on purpose. It reads only givens and produces a target nothing consumes, so once the data is dropped there is nothing for it to connect to — it is the only such step in either arm. Disjoint networks are laid out smallest first, which is what brings it to the top rather than leaving it stranded at the bottom looking like a mistake.

Plan topology only. The givens here resolve against a copied pool, so the plan key is not E2's published one.
