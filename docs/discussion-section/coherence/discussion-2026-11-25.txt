Here we demonstrated radical interoperability between bioinformatics tools using Metasmith. Composing a bioinformatics pipeline today means writing its topology by hand, which takes fluency in both the tools and the workflow system that runs them. Metasmith shows that much of this topology can be derived instead. Each tool is described once, by a contract stating its required inputs and promised outputs using data types such that a symbolic solver can generate workflows dynamically that compile into Nextflow for execution. Because every contract is written against one shared vocabulary, adding a tool means writing one contract rather than routing for every tool it must connect to. Metasmith was demonstrated to reproduce and capture bioinformatics pipelines ranging from well-developed to bespoke. By integrating these pipelines into a shared type system, we further showed how these different pipelines can be stitched together in response to user intent.

Types are what join tools: if the output type of one tool satisfies the input type of another, the two can be chained. A type must therefore describe how data can be used, whereas earlier workflow systems typed what data are, each more richly than the last. Galaxy assigns every dataset a format class. KBase goes further, with versioned schemas that record properties such as a read library's pairing and sequencing technology, yet its apps still accept data by type name alone (Arkin 2018). SADI came closest, defining classes by the properties the data carry (Wilkinson 2011), but those properties still record what the data are rather than what they are ready for. Whether a set of reads can go to a given assembler depends on the state they have reached: the platform that produced them, whether they are paired, and whether they have been trimmed or depleted of host sequence. None of these systems uses that state to decide which tool may take the data. Metasmith's types are sets of properties chosen to capture it, so that a tool, described once by its contract, can be chained with every tool whose types it satisfies. Types are thus the means by which tools interoperate.

Interoperability hinges on a shared vocabulary, and a shared vocabulary requires a standard adopted by a community; as a new tool, Metasmith has neither. Existing standards fall short in two ways. EDAM, which bio.tools and CWL use to annotate tools and files, describes what data are and which operations act on them, but not the state the data have reached, and without that state a planner can produce plans that run but are wrong (Lamprecht 2021). BioMoby's object ontology lived in a central registry, and workflows built on it decayed as the registry and its services disappeared (Zhao 2012). Introducing a new standard of our own would be counterproductive, since where many standards compete, there is in effect no standard. We therefore adopted local namespaces that serve specific cases, to be expanded and joined as they are adopted; being local, they cannot decay with a remote server. Users own the vocabulary as they own the rest of the stack, so our claim is narrower: the type system is expressive enough to capture use cases such as those in the Results. What we offer is less a vocabulary than a principle for building one, namely that a type should draw exactly the distinctions that decide which tools can take the data. Which vocabulary becomes standard is left to use.

Routing is currently the developer's job, and so is making the parts of a pipeline reusable. In Nextflow, the unit of work is the process, a step written for one pipeline rather than a module designed for reuse, and the framework offers no mechanism that tells another pipeline which data a process can take. FlowCraft went further, assembling pipelines from components whose declared input and output types are checked between neighbours, but the developer still sets their order. SADI went further again, describing each web service by the properties it consumes and produces so that services could be found by query (Wilkinson 2011), yet a query spanning several services still spelled out the route. In each case, routing means taking data through the states each tool requires, and the developer works out those steps by hand. Manual routing maximises expressiveness, but it places the responsibility for modularity on the developer, who has little incentive to make a pipeline interoperable and modular while pursuing immediate research goals; the goals of the community are longer term and do not align with those of its members. The result is reimplementation: the GATK Best Practices pipeline alone has over 200 implementations on GitHub (Wratten 2021).

If the route were derived rather than written, every module would be reusable at no extra cost to its developer, aligning the incentive of the individual, a faster route to a running pipeline, with that of the community, reuse and reproducibility; this is what automated planning promises. A planner accepts a join only when the output type of one tool satisfies the input type of the next, so every plan it returns is valid by construction; its search is systematic, the same request returns the same plan, and every join carries a reason that a reviewer can check. APE showed that such planning can compose bioinformatics workflows from annotated tools (Kasalica 2020). Earlier planners could not reach their full potential, however, and two things held them back. The first was their types. Types that describe what data are let invalid plans through as candidates, and where the vocabulary was fixed, people had to supply the structure instead: Wings, for example, specialises templates written by experts rather than composing new workflows (Gil 2011). The second was execution, since a plan had no clear path to a protocol that a machine could execute. Planning also acts before execution, which limits the cases a plan can cover. Metasmith already finds strong plans, which remain valid under every outcome in the output sets that contracts declare (Cimatti 2003), but conditional planning, which branches on data observed at run time (Peot 1992), and strong cyclic planning, which allows loops such as refining a product until it meets a threshold (Cimatti 2003), have yet to be implemented. LLM agents remove the obstacle of execution, because they can compose and run tools directly, in Nextflow or in a shell, but they do so without the guarantees that planning provides.

When an agent writes a pipeline from scratch, each step is an unconstrained guess. Models invent tools and set incompatible parameters (Alam 2025), and because accuracy on composed tasks falls as steps are added (Dziri 2023), these errors compound over the length of a pipeline. A natural remedy is to restrict the agent to a curated catalogue, so that it can no longer invent what it calls; Biomni, for example, retrieves from 150 tools, 105 software packages and 59 databases (Huang 2025). A catalogue fixes what can be called, however, not how calls connect, and recent benchmarks locate the remaining failures at exactly these joins. On BioAgent Bench, correct high-level pipeline construction did not guarantee correct steps: agents carried corrupted inputs through to incorrect results without flagging them, and one selected a decoy file because its name matched (Fa 2026). On FlowBench, failures came from incorrect toolchain selection rather than formatting errors, plans written without a dependency schema came out as edgeless graphs, and models repaired faults by forcing a clean exit while leaving the data invalid (Kurjan 2026). Each of these runs to completion and returns plausible output, because nothing checks that one step's output is a valid input to the next. The guarantees of planning close this gap: a stronger model raises the odds that a join is right, but only types make a join checkable, and LLMs cannot reliably verify their own plans. Agents and planners are therefore complementary, as has been argued for planning in general (Kambhampati 2024): the planner guarantees that every join is valid, while the agent turns a question into a target and ranks the valid plans, which matters because redundant tools for the same task disagree widely (Han 2025; Wu 2024; Hsieh 2024).

Typed contracts are also accessible at different levels of expertise. Metasmith's interfaces form a hierarchy of levels, each catering to an audience that trades a different amount of expressiveness for accessibility, and the levels follow the path from intent to execution: biologists choose data and a target from templates in the GUI, bioinformaticians shape requests and plans through the notebook, API or command line, and tool developers write the contracts and types on which execution rests. Because each level builds on the one below, a contract written once is available at every level above it. Loach et al. (2026) describe flexibility and support as a trade-off on which Galaxy and Nextflow each fix a point; Metasmith lets the user choose where to stand. Since execution is deferred to Nextflow, plans gain its portability and its extensibility to new platforms, running on local machines, HPC schedulers, cloud batch services and Kubernetes, with containers or conda environments. Users therefore own the full stack down to the hardware. On a public Galaxy server, by contrast, modifying the system or reaching the compute layer goes through a central authority, and the alternative is to stand up the full server oneself, which is much harder than running a user-facing execution framework such as Nextflow. The levels are not yet complete: adding a new tool still takes expertise that the GUI does not support, only local and Slurm execution were tested here, and accessibility has not been measured in a user study. Some compute, moreover, is too specialised to hand over. Sharing an analysis today means shipping the whole factory, with the tools, environments, references and expertise needed to run it, when the owner may only want to supply the product. In a decentralised compute market, providers could offer their compute as typed contracts and run it themselves, and the planner could place each step on whichever offer fits. Offers could carry track records such as runtime, cost and benchmark scores, and paying providers to keep their offers alive would answer the decay that ended earlier service registries.
