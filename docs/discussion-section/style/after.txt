Types are what join tools. Two tools can be chained if the output type of one satisfies the input type of the other, so a type must describe how data can be used. Earlier workflow systems instead typed what data are, each more richly than the last. Galaxy assigns every dataset a format class. KBase goes further with versioned schemas that record properties such as the pairing and sequencing technology of a read library, but its apps still accept data by type name alone {Arkin, 2018 #106}. SADI came closest by defining classes through the properties the data carry {Wilkinson, 2011 #85}, but these properties still record what the data are rather than what they are ready for. The state reached by a set of reads, namely the platform that produced them, whether they are paired, and whether they have been trimmed or depleted of host sequence, decides whether they can be given to a particular assembler. None of these systems use this state to decide which tool can take the data. Metasmith's types are sets of properties chosen to capture this state, such that a tool described once by its contract can be chained with every tool whose types it satisfies. Types are therefore the means by which tools interoperate.

Interoperability hinges on a shared vocabulary, which requires a standard adopted by a community. Metasmith, as a new tool, has neither. Existing standards fall short in two ways. EDAM, which bio.tools and CWL use to annotate tools and files, describes what data are and which operations act on them, but not the state the data have reached. A planner without this state can produce plans that run but are wrong {Lamprecht, 2021 #88}. BioMoby kept its object ontology in a central registry, and workflows built on it decayed as the registry and its services disappeared {Zhao, 2012 #6}. A new standard from Metasmith would be counterproductive, since many competing standards amount to no standard at all. Metasmith therefore adopts local namespaces that serve specific cases and are to be expanded and joined as they are adopted. Such namespaces, being local, cannot decay with a remote server. Metasmith does not prescribe the vocabulary, just as it does not prescribe the rest of the stack, and its claim is narrower in the absence of a standard. The claim is that the type system is expressive enough to capture use cases such as those in the Results. Metasmith offers less a vocabulary than a principle for building one, which is that a type should draw exactly the distinctions that decide which tools can take the data. The question of which vocabulary becomes standard is left to use. Tools described as typed contracts, rather than the vocabulary that emerges, drive interoperability.

Types describe the valid connections between tools, but the route from end to end must still be chosen. Routing is currently the developer's job, as is making the parts of a pipeline reusable. Nextflow's unit of work is the process, a step written for one pipeline rather than a module designed for reuse, and the framework has no mechanism to tell another pipeline which data a process can take. FlowCraft went further by assembling pipelines from components whose declared input and output types are checked between neighbours, but the developer still sets the order of these components. SADI went further again by describing each web service with the properties it consumes and produces so that services could be found by query {Wilkinson, 2011 #85}. A query spanning several services, however, still spelled out the route. Routing in each case means taking data through the states that each tool requires, and the developer works out these steps by hand. Manual routing maximizes expressiveness, but places the responsibility for modularity on the developer. The developer has little incentive to make a pipeline interoperable and modular while pursuing immediate research goals, and the longer-term goals of the community do not align with those of its members. Reimplementation is the result, and the GATK Best Practices pipeline alone has over 200 implementations on GitHub {Wratten, 2021 #27}.

A route that is derived rather than written would make every module reusable at no extra cost to its developer. Derived routes would align the incentive of the individual for a faster path to a running pipeline with the incentive of the community for reuse and reproducibility, and automated planning promises such routes. A planner accepts a join only when the output type of one tool satisfies the input type of the next, so every plan it returns is valid by construction. Its search is systematic, so the same request returns the same plan, and every join carries a reason that a reviewer can check. APE showed that such planning can compose bioinformatics workflows from annotated tools {Kasalica, 2020 #94}. Earlier planners, however, could not reach their full potential, and two obstacles held them back. The first was their types. Types that describe what data are let invalid plans through as candidates, and people had to supply the structure instead where the vocabulary was fixed. Wings, for example, specializes templates written by experts rather than composing new workflows {Gil, 2011 #86}. The second was execution, since a plan had no clear path to a protocol that a machine could execute. Metasmith removes both obstacles. Its types carry the state that decides which tools can take the data, so invalid joins never become candidates, and every plan compiles to Nextflow, so it runs as written. Planning also acts before execution, which limits the cases a plan can cover. Metasmith already finds strong plans, which remain valid under every outcome in the output sets declared by contracts {Cimatti, 2003 #107}. Conditional planning, which branches on data observed at run time {Peot, 1992 #113}, and strong cyclic planning, which allows for loops such as refining a product until it meets a threshold {Cimatti, 2003 #107}, however, have yet to be implemented. LLM agents have been applied as an alternative to planners, one that can also execute by composing and running tools directly in Nextflow or a shell. Agents, however, do so without the guarantees that planning provides.

LLM agents can propose whole pipelines, but nothing checks the joins between their steps. An agent writing a pipeline from scratch makes each step an unconstrained guess. Models invent tools and set incompatible parameters {Alam, 2025 #109}, and these errors compound over the length of a pipeline, since accuracy on composed tasks falls as steps are added {Dziri, 2023 #111}. A curated catalogue is a natural remedy that restricts the agent so that it can no longer invent what it calls. Biomni, for example, retrieves from 150 tools, 105 software packages and 59 databases {Huang, 2026 #104}. A catalogue, however, fixes what can be called, not how calls connect, and recent benchmarks locate the remaining failures at exactly these joins. Correct high-level pipeline construction on BioAgent Bench did not guarantee correct steps. Agents carried corrupted inputs through to incorrect results without flagging them, and one agent selected a decoy file because its name matched {Fa, 2026 #110}. Failures on FlowBench came from incorrect toolchain selection rather than formatting errors, and models repaired faults by forcing a clean exit while leaving the data invalid {Kurjan, 2026 #108}. Each of these runs finishes and returns plausible output, since nothing checks that the output of one step is a valid input to the next. The guarantees of planning close this gap. A stronger model raises the odds that a join is right, but only a check of type fit, as in the planners above, makes a join valid by construction, and LLMs cannot reliably verify their own plans. Agents and planners are therefore complementary, as has been argued for planning in general {Kambhampati, 2024 #112}. A symbolic solver can generate the valid routes between typed contracts, while an agent turns a question into a target and supplies the heuristics that guide search and rank the valid plans. Ranking matters since redundant tools for the same task disagree widely {Han, 2025 #36;Wu, 2024 #101;Hsieh, 2024 #102}.

Typed contracts are accessible at different levels of expertise, from stating intent to supplying compute, which extends their use beyond routing. Metasmith's interfaces form a hierarchy of levels, each catering to an audience that spends a different amount of expressiveness to buy accessibility. The levels follow the path from intent to execution. Biologists choose data and a target from templates in the GUI, bioinformaticians shape requests and plans through the notebook, API or command line, and tool developers write the contracts and types on which execution rests. Each level builds on the one below, so a contract written once is available at every level above it. Loach et al. {Loach, 2026 #93} describe flexibility and support as a trade-off on which Galaxy and Nextflow each fix a point, whereas Metasmith lets the user choose where to stand. Plans are executed by Nextflow and so gain its portability and extensibility to new platforms, running on local machines, HPC schedulers, cloud batch services and Kubernetes, with containers or conda environments. Users therefore own the full stack down to the hardware. A public Galaxy server, in contrast, places modification of the system or access to the compute layer behind a central authority, and the alternative of standing up a full server oneself is much harder than running a user-facing execution framework like Nextflow. The levels are not yet complete. Adding a new tool still takes expertise that the GUI does not support, only local and Slurm execution were tested here, and accessibility has not been measured in a user study. Users, who own the stack down to the hardware, could also offer it to others, which matters since some compute is too specialized to hand over. Sharing an analysis today means shipping the whole factory, including the tools, environments, references and expertise needed to run it, when the owner may only want to supply the product. Providers in a decentralized compute market could offer their compute as typed contracts and run it themselves, and the planner could place each step on whichever offer fits. Offers could carry track records such as runtime, cost and benchmark scores, and paying providers to keep their offers alive would address the decay that ended earlier service registries. The typed contract is the common unit in each case. It joins tools, lets a solver choose the route between them, and could let providers offer their compute.
