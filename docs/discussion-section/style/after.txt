Types are what join tools. If the output type of one tool satisfies the input type of another, then the two tools can be chained, so a type must describe how data can be used. Earlier workflow systems instead typed what data are, each more richly than the last. Galaxy assigns every dataset a format class. KBase goes further with versioned schemas that record properties such as the pairing and sequencing technology of a read library, but its apps still accept data by type name alone {Arkin, 2018 #106}. SADI came closest by defining classes through the properties the data carry {Wilkinson, 2011 #85}, but these properties still record what the data are rather than what they are ready for. Whether a set of reads can be given to an assembler depends on the state they have reached, such as the platform that produced them, whether they are paired, and whether they have been trimmed or depleted of host sequence. None of these systems use this state to decide which tool can take the data. In Metasmith, types are sets of properties chosen to capture this state, such that a tool described once by its contract can be chained with every tool whose types it satisfies. In this way, types are the means by which tools interoperate.

Interoperability hinges on a shared vocabulary, which requires a standard adopted by a community. As a new tool, Metasmith has neither. Existing standards fall short in two ways. EDAM, which bio.tools and CWL use to annotate tools and files, describes what data are and which operations act on them, but not the state the data have reached. Without this state, a planner can produce plans that run but are wrong {Lamprecht, 2021 #88}. BioMoby kept its object ontology in a central registry, and workflows built on it decayed as the registry and its services disappeared {Zhao, 2012 #6}. Introducing a new standard of our own would be counterproductive, since many competing standards amount to no standard at all. We therefore adopted local namespaces that serve specific cases and can be expanded and joined as they are adopted. Since these namespaces are local, they cannot decay with a remote server. We do not prescribe the vocabulary, just as we do not prescribe the rest of the stack, and without a standard our claim is narrower. We claim only that the type system is expressive enough to capture use cases such as those in the Results. Rather than a vocabulary, we offer a principle for building one, which is that a type should draw exactly the distinctions that decide which tools can take the data. Which vocabulary becomes the standard is left to usage, but whichever emerges, it is tools described as typed contracts over this vocabulary that drive interoperability.

Types describe the valid connections between tools, but the route from end to end must still be chosen. Routing is currently the developer's job, as is making the parts of a pipeline reusable. In Nextflow, the unit of work is the process, which is a step written for one pipeline rather than a module designed for reuse, and the framework has no mechanism to tell another pipeline which data a process can take. FlowCraft went further by assembling pipelines from components whose declared input and output types are checked between neighbours, but the order of these components is still set by the developer. SADI went further again by describing each web service with the properties it consumes and produces so that services could be found by query {Wilkinson, 2011 #85}. However, a query spanning several services still spelled out the route. In each case, routing means taking data through the states that each tool requires, and the developer works out these steps by hand. Manual routing maximizes expressiveness, but places the responsibility for modularity on the developer. There is little incentive to make a pipeline interoperable and modular when dealing with immediate research goals, and the longer-term goals of the community do not align with those of its members. The result is reimplementation, with the GATK Best Practices pipeline alone having over 200 implementations on GitHub {Wratten, 2021 #27}.

If the route were derived rather than written, every module would be reusable at no extra cost to its developer. This would align the incentive of the individual for a faster route to a running pipeline with the incentive of the community for reuse and reproducibility, and is what automated planning promises. A planner accepts a join only when the output type of one tool satisfies the input type of the next, so every plan it returns is valid by construction. Its search is also systematic, such that the same request returns the same plan and every join carries a reason that a reviewer can check. APE showed that this kind of planning can compose bioinformatics workflows from annotated tools {Kasalica, 2020 #94}. However, earlier planners could not reach their full potential, and two obstacles held them back. The first was their types. Types that describe what data are let invalid plans through as candidates, and where the vocabulary was fixed, the structure had to be supplied by people instead. For example, Wings specializes templates written by experts rather than composing new workflows {Gil, 2011 #86}. The second was execution, since a plan had no clear path to a protocol that a machine could execute. Metasmith removes both obstacles. Its types carry the state that decides which tools can take the data, so invalid joins never become candidates, and every plan compiles to Nextflow, so it runs as written. Since planning acts before execution, there are also cases that a plan cannot cover. Metasmith already finds strong plans, which remain valid under every outcome in the output sets declared by contracts {Cimatti, 2003 #107}. However, conditional planning, which branches on data observed at run time {Peot, 1992 #113}, and strong cyclic planning, which allows for loops such as refining a product until it meets a threshold {Cimatti, 2003 #107}, have yet to be implemented. LLM agents have been applied as an alternative to planners, one that can also execute by composing and running tools directly in Nextflow or a shell, but without the guarantees that planning provides.

LLM agents can propose whole pipelines, but nothing checks the joins between their steps. When an agent writes a pipeline from scratch, each step is an unconstrained guess. Models invent tools and set incompatible parameters {Alam, 2025 #109}, and since accuracy on composed tasks falls as steps are added {Dziri, 2023 #111}, these errors compound over the length of a pipeline. A natural remedy is to restrict the agent to a curated catalogue so that it can no longer invent the tools it calls. Biomni, for example, retrieves from 150 tools, 105 software packages and 59 databases {Huang, 2026 #104}. However, a catalogue fixes what can be called, not how calls connect, and recent benchmarks locate the remaining failures at exactly these joins. On BioAgent Bench, correct high-level pipeline construction did not guarantee correct steps, as agents carried corrupted inputs through to incorrect results without flagging them, and one agent selected a decoy file because its name matched {Fa, 2026 #110}. On FlowBench, failures came from incorrect toolchain selection rather than formatting errors, and models repaired faults by forcing a clean exit while leaving the data invalid {Kurjan, 2026 #108}. Each of these runs to completion and returns plausible output, since nothing checks that the output of one step is a valid input to the next. The guarantees of planning close this gap. A stronger model raises the odds that a join is right, but only a check of type fit, as in the planners above, makes a join valid by construction, and LLMs cannot reliably verify their own plans. Agents and planners are therefore complementary, as has been argued for planning in general {Kambhampati, 2024 #112}. A symbolic solver can generate the valid routes between typed contracts, while an agent turns a question into a target and supplies the heuristics that guide search and rank the valid plans. This matters since redundant tools for the same task disagree widely {Han, 2025 #36;Wu, 2024 #101;Hsieh, 2024 #102}.

Beyond routing, typed contracts are accessible at different levels of expertise, from stating intent to supplying compute. Metasmith's interfaces form a hierarchy of levels, each catering to an audience that spends a different amount of expressiveness to buy accessibility. These levels follow the path from intent to execution. Biologists choose data and a target from templates in the GUI, bioinformaticians shape requests and plans through the notebook, API or command line, and tool developers write the contracts and types on which execution rests. Since each level builds on the one below, a contract written once is available at every level above it. Loach et al. {Loach, 2026 #93} describe flexibility and support as a trade-off on which Galaxy and Nextflow each fix a point, whereas Metasmith lets the user choose where to stand. Since execution is deferred to Nextflow, plans gain its portability and extensibility to new platforms, running on local machines, HPC schedulers, cloud batch services and Kubernetes, with containers or conda environments. This lets users own the full stack down to the hardware. In contrast, modifying the system or reaching the compute layer on a public Galaxy server goes through a central authority, and the alternative is to stand up the full server oneself, which is much harder than running a user-facing execution framework like Nextflow. The levels are not yet complete. Adding a new tool still takes expertise that the GUI does not support, only local and Slurm execution were tested here, and accessibility has not been measured in a user study. Owning the stack down to the hardware also means that users could offer it to others, which matters since some compute is too specialized to hand over. Sharing an analysis today means shipping the whole factory, including the tools, environments, references and expertise needed to run it, when the owner may only want to supply the product. In a decentralized compute market, providers could offer their compute as typed contracts and run it themselves, and the planner could place each step on whichever offer fits. Offers could carry track records such as runtime, cost and benchmark scores, and paying providers to keep their offers alive would address the decay that ended earlier service registries. In each case, the typed contract is the common unit that joins tools, lets a solver choose the route between them, and could let providers offer their compute.
