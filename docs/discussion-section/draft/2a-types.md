# 2a draft: types of use (accepted by Tony, 2026-11-24)

Key message: types join tools, so they must describe how data can be used, where earlier type systems describe format, content or structure.
Points: chaining rule; prior systems (format, content, structure; SADI closest in approach); reads-before-assembly case; KBase records the properties as fields but apps match by type name (verified on the live Workspace: KBaseFile.PairedEndLibrary-2.1 vs SingleEndLibrary-2.1; sequencing_tech, single_genome as fields; app inputs by valid_ws_types); Metasmith property sets.
Ref added: Arkin 2018, Nat Biotechnol 36(7):566-569, doi 10.1038/nbt.4163.

Accepted draft:

Types are what join tools: if the output type of one tool satisfies the input type of another, the two can be chained. A type must therefore describe how data can be used, whereas earlier workflow systems typed what data are, each more richly than the last. Galaxy assigns every dataset a format class. KBase goes further, with versioned schemas that record properties such as a read library's pairing and sequencing technology, yet its apps still accept data by type name alone (Arkin 2018). SADI came closest, defining classes by the properties the data carry (Wilkinson 2011), but those properties still record what the data are rather than what they are ready for. Whether a set of reads can go to a given assembler depends on the state they have reached: the platform that produced them, whether they are paired, and whether they have been trimmed or depleted of host sequence. None of these systems uses that state to decide which tool may take the data. Metasmith's types are sets of properties chosen to capture it, so that a tool, described once by its contract, can be chained with every tool whose types it satisfies. Types are thus the means by which tools interoperate.
