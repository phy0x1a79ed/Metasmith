# 1a draft: manual routing (in d2 2026-11-25, pending Tony's review)

Types describe the valid connections between tools, but the route from end to end must still be chosen. Routing is currently the developer's job, as is making the parts of a pipeline reusable. In Nextflow, the unit of work is the process, which is a step written for one pipeline rather than a module designed for reuse, and the framework has no mechanism to tell another pipeline which data a process can take. FlowCraft went further by assembling pipelines from components whose declared input and output types are checked between neighbours, but the order of these components is still set by the developer. SADI went further again by describing each web service with the properties it consumes and produces so that services could be found by query {Wilkinson, 2011 #85}. However, a query spanning several services still spelled out the route. In each case, routing means taking data through the states that each tool requires, and the developer works out these steps by hand. Manual routing maximizes expressiveness, but places the responsibility for modularity on the developer. The developer has little incentive to make a pipeline interoperable and modular when pursuing immediate research goals, and the longer-term goals of the community do not align with those of its members. The result is reimplementation, with the GATK Best Practices pipeline alone having over 200 implementations on GitHub {Wratten, 2021 #27}.
