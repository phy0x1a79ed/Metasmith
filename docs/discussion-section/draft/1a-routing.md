# 1a draft: manual routing (in d2 2026-11-25, pending Tony's review)

Routing is currently the developer's job, and so is making the parts of a pipeline reusable. In Nextflow, the unit of work is the process, a step written for one pipeline rather than a module designed for reuse, and the framework offers no mechanism that tells another pipeline which data a process can take. FlowCraft went further, assembling pipelines from components whose declared input and output types are checked between neighbours, but the developer still sets their order. SADI went further again, describing each web service by the properties it consumes and produces so that services could be found by query (Wilkinson 2011), yet a query spanning several services still spelled out the route. In each case, routing means taking data through the states each tool requires, and the developer works out those steps by hand. Manual routing maximises expressiveness, but it places the responsibility for modularity on the developer, who has little incentive to make a pipeline interoperable and modular while pursuing immediate research goals; the goals of the community are longer term and do not align with those of its members. The result is reimplementation: the GATK Best Practices pipeline alone has over 200 implementations on GitHub (Wratten 2021).
