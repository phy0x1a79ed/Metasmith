## Solver

**Types.** Types are sets of properties, and each property narrows the range of variation of the data it describes. A type X satisfies a type Y if X has all of the properties of Y, written S(X,Y) ≡ X ⊇ Y (Figure 1A). An abstract type has fewer properties and is therefore satisfied by every more specific type, but not the reverse, as a wooden chair is a chair, though not every chair is wooden. Types are declared in namespaces, which are local YAML files, and are named as namespace::type. The Discussion gives the context for sharing namespaces.

**Contracts.** A contract states the input types a tool requires and the output types it promises. Each use of a contract in a plan is a step, which binds each input to a port whose type satisfies it and exposes one new port per output type. Each port records its lineage, the ports its step consumed. A contract that accepts a general type loses which specific data came in, so a compressor that accepts any file yields only a compressed file. An input can therefore require that its port descends from the port bound to another input of the same step, as when mapping reads to an assembly requires the assembly built from those reads. The constraint requires that exact port, not any ancestor of a matching type, so data from unrelated sources are never joined. Beyond its specification, a contract also declares a protocol for how it can be fulfilled, which holds a Python procedure that runs its tool, its output file names, its resource requests and a container image declared as one of its inputs.

**Optional branching.** Some tools write one of several sets of outputs, decided only at run time, so a contract can declare alternative output groups, which makes it a fork. A single solve plans for one group of each fork. Every other outcome is planned from the plan up to the fork and merged into the same plan, so the plan holds a route below every outcome. At run time each step runs as a task that writes only the group it produced, and the branches it did not take stay empty.

**Planning.** From a library of contracts, the user's data (the givens) and a requested output (the target), the planner must find a plan. We framed planning as a tree search of the Monte Carlo tree search (MCTS) family, in which each node is a search state, a partial plan, and each edge adds one step. The root holds only the given step and the target step. The search walks from the root until it reaches a solved state, one with every input bound. The frontier holds every step that could be added next, one entry per valid binding of a contract's inputs to existing ports. Before the search, a breadth-first search (BFS) that ignores lineage walks back from the target's inputs to the contracts that can produce them, level by level, so each contract's distance is the fewest steps between it and the target. The BFS also counts the routes from each contract to the target and drops contracts it never reaches. A predictor upper confidence bound applied to trees (PUCT) rule scores each frontier step a, and the highest is grown next,

U(a) = Q(t) + c·P(a)·√(1+N) / (1+n(t)),

where t is the contract of a, Q(t) is the mean reward t has earned, n(t) is how often t was picked, N is the total number of picks, and P(a) is a prior favoring steps closer to the target and with more routes to it. The first term exploits contracts that made progress, and the second favors promising, rarely tried steps and shrinks as a contract is picked. The reward is the gain in the target's satisfied inputs, or 1 when the plan is solved. The search uses no random rollouts and stops at the first solved plan or at a fixed iteration limit. A seeded random-number generator and a fixed iteration order make the same request return the same plan.

**Refinement.** Lineage makes the search path-dependent and PUCT is optimistic, so the first solved plan is not guaranteed to be the simplest. A short refinement search therefore tries single-edge swaps, each of which rebinds one step's input to another existing port and rebuilds every step downstream so that its lineage stays correct. A candidate must still pass the plan conditions of the witness checker (see Verification), chiefly that every step can be scheduled and every lineage constraint holds. Valid candidates are ranked first by how few distinct ports their lineage constraints anchor to, then by how close those anchors sit to the inputs that need them. The same PUCT rule picks which candidate to expand for a fixed budget of rounds. The best valid plan wins, and steps no longer connected to the target are removed. In development testing, the vast majority of plans were already optimal before refinement.

**Verification.** Proving a search-based solver correct is hard, because its path depends on heuristics and on the order in which it explores. Checking a finished plan is far simpler, so we wrote a witness checker, a small program that tests a finished plan, and proved it correct instead. Every plan the solver returns passes through the checker, and a plan that fails is refused with the condition it broke. The checker reads only the problem and the plan and tests ten conditions, among them that every binding satisfies its input type and lineage, every port has one producer and is given or produced before use, the steps form a directed acyclic graph (DAG), and the target appears exactly once. A Lean 4 proof shows that the checker's Rust code returns true exactly when a plan meets the formal specification, so every plan it accepts meets that specification.

## Specification

**Interfaces.** Metasmith exposes one set of operations through three modalities, a Python API, a command line and a graphical user interface (GUI), so a user can take the same actions through any of them. A single operations layer defines every action, and each modality is a thin front end over it. The actions cover registering typed data, choosing contract libraries and targets, planning, deploying to a worker, running and monitoring, collecting results, and managing the cache. The Python API calls the operations directly, the command line (metasmith, or msm) maps each operation to a subcommand, and the GUI exposes them as forms around saved templates. Writing a new contract is the exception, since a contract is itself a Python file.

**Inputs.** A user's data enter as a data library, which lists files and values, each registered with a type. A type can be picked from the types the contracts require, or composed directly from properties. Each registered file or value is an instance, and an instance can declare parents, so lineage among the instances is recorded before planning. The instances are the plan's givens, which the planner sees as one given step with no inputs, whose ports carry their types and declared lineage.

**Outputs.** The user lists the targets, the types of data to produce, and the planner builds one target contract whose inputs are those types and which has no outputs. A target can name other targets as parents, which become lineage constraints on the target contract's inputs, as for any contract. Because the target is an ordinary contract, the planner needs no special case, and a plan is solved once the target step's inputs are bound.

**Parallel cases.** Inputs often vary slightly in form, yet the user wants a common result from all of them, and some inputs also need targets of their own. A specification can therefore hold several cases, each with its own givens and targets, and each case is solved on its own. The solved plans are merged step by step, so a step that several cases share runs once in the workflow.

**Variadic contracts.** Some tools take a variable number of inputs of one type, so a contract can mark one input as variadic. The user matches the variadic input to an actual set by naming, on a target, the member types that fill it, and each member must satisfy the variadic input's type. The named members specify exactly which tools form an ensemble. The planner then replaces the variadic input with one ordinary input per named member, and the search plans a route to each member like any other input. Outputs of the expanded contract carry a property naming the set, so outputs of different sets are different types and neither satisfies the other.

## Execution

**Compiling to Nextflow.** Each step of the plan compiles to one Nextflow process, and each port to one channel. Each item in a channel carries a lineage index naming the instances it descends from. Channels are joined only by merging, copying and grouping. A contract names the input it groups by and a batch size, the number of index items per task. At compile time, each other input of a grouping step is classed by its relation to the index input in the plan, as an ancestor, a descendant, a sibling that shares an ancestor, or unrelated. At run time, each index item collects its matches through their lineage indices. An ancestor is found by the id in the item's own index, a descendant by the item's id in the descendant's index and a sibling by a shared ancestor id, while an unrelated input is passed whole. A group is released once every item it expects has arrived, as counted by stamps that the producing tasks add to each output, or else when the channel closes. Each process runs one bootstrap command, which loads its step from the staged plan, matches the files Nextflow staged to the step's inputs by lineage, and calls the contract's protocol with a context of input paths, output paths and a shell. The protocol runs its tool in the tool's own container. The compiled workflow can be deployed to a designated worker home (msm_home), on a local filesystem or a remote machine.

**Running workflows.** A worker home is declared as a path, plus an SSH address if it is remote. A remote deploy uses the existing SSH configuration and otherwise works as a local one. Staging writes a workspace into the home, holding the Nextflow workflow, input manifests, parameter files and a launcher script. The launcher runs the Nextflow driver inside a container, detached from the user's session, and a relay started outside that container lets the driver start each step's container from inside its own. Running the launcher by hand has the same effect. Every Nextflow executor is available, and local and SLURM were tested and ship as presets. Each run records a DAG of the plan, the Nextflow logs and a lineage table for every output and intermediate.

**Caching.** A data library is a plain directory of files with a manifest recording each instance's type, and outputs are written in the same format with their lineage. Results can therefore be reused as inputs in any later run, so a worker holds a pool of data products across runs. Caching has to work across runs, and Metasmith keeps its own cache on top of Nextflow's. Every data instance has an id. A file of 1 MiB or less in a data library is identified by its path within the library and its bytes, and a larger file or a directory by its absolute path and modification time, since inputs reach hundreds of gigabytes. A recorded id is re-derived when its file changes. Alternatively, data already on the worker's machine can be imported into its pool directly by path and declared type, a shortcut that skips the library, and each import receives a fresh id assigned without reading the data. The cache key of a task is a hash of its contract, protocol source included, and of the ids of the instances it consumed. Nothing about its outputs takes part. Each output takes its id from that key. When a task succeeds, its outputs are stored in the worker's cache under its key. Before submitting each task, Metasmith looks up its key. A miss goes to the step's process, and a hit goes to a light twin process that places the stored outputs into Nextflow's work directory, so downstream steps and publishing see an ordinary finished task. A result is reused whenever the same contract runs on the same inputs, even in a different workflow. Editing a protocol invalidates its results and those of its descendants, while changing compute resources does not.

## Benchmarks

**MAG comparison.** MAGs were compared within each sample and binner with skani 0.2.2 (--min-af 0). Identity is the average nucleotide identity (ANI) multiplied by the smaller of the two aligned fractions, and two MAGs are reciprocal partners when each is the other's best match with an ANI of at least 95% and both aligned fractions of at least 50%.

**Lines of code.** Lines were counted without blank lines, comments or stub sections. In nf-core/mag, the input and output blocks of each process count as channel declarations, and workflow-level lines in the subworkflows our configuration reaches count as routing. In Metasmith, the type declarations of each contract count as logistics, and the rest of its protocol counts as procedure.

**vOTU comparison.** vOTUs were compared with skani 0.2.2 (--small-genomes --min-af 15). A published vOTU is recovered if a reproduced vOTU matches it at an ANI of at least 95% over at least 85% of its length. For one-to-one pairing, identity is ANI multiplied by the published vOTU's aligned fraction, and the pairing that maximizes total identity is found with the sparse Jonker-Volgenant algorithm in SciPy, which lets vOTUs stay unpaired (43, 44).

**GEM comparison.** The reproduction built GEMs with CarveMe 1.2.2 (-g M8 --fbc2, metaGEM's M8 medium), using DIAMOND 0.9.30 (--more-sensitive --top 10) and CPLEX 22.2. Each reproduced GEM was compared with the published GEM of the same bin by the Jaccard index of their BiGG reaction identifiers.

**Update ablation.** On a stratified 10% of bins (1,408), the components of the update were introduced one at a time, namely the BiGG gene reference, the universal model, the CarveMe 1.6.6 code, gap filling, DIAMOND and SCIP. Each component's share of the drop in median Jaccard index was measured.

**KofamScan annotation.** On the same 1,408 bins, KofamScan 1.3.0 (E ≤ 0.01, with per-KO adaptive thresholds) annotated the ORFs. KOs were mapped to reactions through KEGG ko2reaction (release 119) and MetaNetX 4.5, and DIAMOND hits were mapped from BiGG genes to MetaNetX reactions in the same way.

**Compute cost.** Core-hours are SLURM allocated time, allocated cores multiplied by elapsed time, summed over every attempt, with cached steps counted as zero. Energy and CO₂ were estimated with Green Algorithms (76) [TODO: CPU model, power per core, memory power, PUE and carbon intensity].
