# metasmith docs overhaul: one public API, task tutorials on three surfaces

## Context

metasmith has four user surfaces: the CLI, the Python API, the web GUI, and the GUI's live in-app tutorials. The written docs teach only a stale notebook path. This plan rebuilds the docs around task tutorials whose every step shows the same action three ways: a CLI command, a Python script, and a link into the running GUI. Two single points of control keep the surfaces from drifting. A registry of public operations generates the CLI, the Python API's help and the reference pages. Each tutorial page is the one source for its docs, its in-app tutorial and its tests. Work happens in scope `metasmith/engine/docs` (branch `feat/engine/docs`, from `feat/dev`), with a live preview of the pages and the GUI throughout.

## Issues

- I1. The docs homepage and tutorials teach only the notebook API, and nothing mentions `msm gui` or its in-app tutorials.
- I2. The notebook pages call API that no longer exists (`Std()`, `context.Get`, `ExecWithEnv().ifContainerDo`, `AddRequirement(node=)`, `TransformInstance` without `group_by`), and `my_first_agent` cannot run on 0.24.
- I3. CLI help, the CLI reference tables, the agentic pages and the GUI each restate the operations by hand, and they drift: the agentic pages miss about nine commands and claim parity that does not exist.
- I4. `msm workflow run` passes its arguments to `ops.runtime.run` in the wrong order: params land in `config_file`, overrides in `params`, stub delay in `resource_overrides` (`coms/cli/workflow.py:148`).
- I5. The surfaces address objects three ways: the GUI by name inside a project, the CLI by file path and workspace task key, Python by in-memory objects. So a tutorial cannot name one object across its tabs.
- I6. Some operations exist on one surface only. Only the GUI has SSH host setup, sample sheets and recipes, sharing, and the solve/run orchestration (in route bodies). The CLI has no templates. Only the CLI and Python have authoring, cache explain/gc, pin/invalidate and direct runs.
- I7. A docs page cannot open the running GUI at a step: the URL hash carries no tutorial state, jumping never creates a step's prerequisites, and replaying from scratch re-mints input ids, so nothing hits the cache.
- I8. No test runs a tutorial's blocks against real infrastructure, no lane targets a remote HPC host, and the remote hosts that tests do name are hard-coded.
- I9. The install page flags Docker as experimental, and the MAMBA (conda) agent runtime has no stated status or test.
- I10. Errors users and agents hit are scattered across scope journals and Antonio's reports, with no list of which are still unfixed.
- I11. Two usage pages are empty stubs, the workflow catalog covers 1 of 12 templates, `tutorials/python.rst` is an orphan, and `README.md` on `feat/dev` and `release` is the viromics scope's write-up.
- I12. `dev/metasmith.sh` has no `--help`, although `AGENTS.md` says every dev script has one.

## High-level goals

- G1. A reader picks a task and finishes it by CLI, by clicking through the GUI, or by writing and running a Python script, switching surfaces at any step.
- G2. A GUI user goes from any tutorial step straight into their running GUI at that point, with the real prior steps already done.
- G3. Every operation is described once, and the CLI help, the Python API help and the reference pages follow from that description.
- G4. Every tutorial page shares one header: the five-step flow, how to use the tutorials, the docs home, and where to go next.
- G5. A reader can look up any module and see what it does on each surface.
- G6. Tutorials run for real in tests: quickly on every change, and fully on a cluster when asked.
- G7. The install and runtime docs state what is supported, and the conda runtime is a working experimental option or gone.
- G8. The user can watch the pages and the GUI live while the work proceeds.
- G9. The user has a list of the errors people actually hit that are still unfixed.

## Acceptance criteria

- The docs preview is reachable through the awm gateway and rebuilds on save. A GUI session from this worktree runs on a fixed port the user tunnels to.
- Each public operation has one registry entry. `msm --help`, every subcommand's help, the Python API's docstrings, the CLI reference page and the per-module reference pages come from it. A golden test pins the generated CLI's verb and flag spelling to what deployed agents call over SSH.
- `msm workflow run --params ... --override ...` reaches `ops.runtime.run` with each value in its own parameter, pinned by a test.
- The CLI and Python can do everything the GUI can, addressing the same project objects by name: SSH hosts, agents, templates, sample sheets, solves, runs, and exporting and importing libraries and solved workflows as files.
- Each tutorial is one page. Its steps' CLI blocks join into a runnable bash script and its Python blocks into a runnable Python script, both offered for download from the page. The in-app tutorial data and the test scripts are extracted from the same page.
- Every tutorial page opens with the shared header and has a GUI-port box defaulting to 8090. Its CLI / Python / GUI tabs switch together across steps and stay chosen across pages.
- A GUI tab link opens `#tutorial/<id>/<step>` in the running GUI. The GUI fast-forwards by running the page's Python script up to that step against its own project, reusing the tutorial's stable objects, and marks the control to use.
- The fast lane checks every tutorial page's structure, every `data-tour` anchor it names, and the CLI golden snapshot, in seconds. The virtual-runtime replay of every tutorial is its own quick lane.
- The slow lane `e2e/hpc` runs every tutorial's bash and Python scripts for real on the host named by `METASMITH_TEST_HPC_HOST`, and skips when it is unset. No hostname appears in test code.
- The install page lists Docker and Apptainer as supported. MAMBA is documented as experimental with the templates it runs, or removed from the GUI picker and the docs.
- A triaged list of unfixed errors from the journals and Antonio's reports exists, and the user has reviewed it.
- No published page references `Std()`, `context.Get`, `ifContainerDo` or `AddRequirement(node=`. The Sphinx build reports no broken internal links.

## Tutorial list

Each tutorial reuses the previous one's objects where it can, so the GUI fast-forward and the cache stay cheap.

1. **Your first workflow: a pangenome on this machine.** Make a local agent. Deploy it. Start a workflow from the pangenome template. Read the recipe. Bind a three-accession sheet. Introduce the lineage constraint on outputs: a heatmap per pangenome, annotations per genome. Solve. Read the DAG. Run. Collect. Open the heatmap.
2. **Run it somewhere else: SSH.** Add an SSH host and key. Check the connection. Make a remote agent. Deploy it. Rerun the same pangenome on it. See what is staged where. Retrieve the results.
3. **Your compute environment: container engines and Nextflow executors.** Docker and Apptainer (and MAMBA, per T15). Image store and offline compute nodes. Setup commands such as `module load`. Nextflow presets: local, slurm, custom config and params. Per-step cpus/mem/time overrides. GPUs.
4. **Declare your own inputs.** Point at your files. Find the right type. Tag entries in the pool. Use pool entries and paths as inputs. Bind a sample sheet from your own CSV. No data transfer beyond what staging does.
5. **Change one thing: reuse, cache and lineage.** Change one input. Rerun. See which steps are reused. Explain a miss. Trace an output's lineage. Pin, invalidate, gc.
6. **An ask with no plan.** Ask for a target the library cannot produce. Read the solve hints. See why it is genuinely unsolvable. Stop there.
7. **Add your own transform: basic.** Scaffold. Contract (requirements and products with types). Protocol (`ExecWithEnv`). Instance. Validate. Run it alone (`msm run`). Add it to a library. Watch the solver pick it.
8. **Add your own transform: advanced.** New types. `group_by` and `InputGroup` (many-to-one). Per-slot lineage. Value params and defaults. Resources and GPUs. Container plus conda recipe. `cacheable`. Multiple products. Provenance and metadata. Stub runs.
9. **Share libraries and solved workflows.** Export a transform library and a solved workflow as files. Hand them over. Import them on another machine and rerun. Save a workflow as a template.

Tutorials 7 and 8 have no GUI actions except enabling the library. Their GUI tab says so and points at the CLI and Python tabs, so the synced tab choice never lands on nothing.

## Approach by task

### T1. Live preview

Run sphinx-autobuild (`dev/metasmith.sh --docs`) on a fixed local port in the background. Register it with `awm gateway register --name metasmith-docs --prefix /msm-docs --url http://127.0.0.1:<port>`, held as a background lease. Start the GUI from this worktree (`./dev/metasmith.sh -r --gui`) on port 8090, with no browser, against a scratch project. Report both URLs and the tunnel command. The preview grows as tasks land.

Gotchas: the lease dies with the session, so the report names the re-register command. Check that live reload's websocket survives the prefix. The GUI must not run workflows on this workstation: its demo agents point at the cluster.

### T2. `workflow run` argument order

Pass keywords from `_cmd_run` to `ops.runtime.run`. Add a unit test that drives the parser and asserts each value lands in its own parameter. This lands first because the bug is live in released builds.

### T3. Error triage

Pull the metasmith scope journals (`scope fetch kind=journal`) and Antonio's reports (scope `engine/fix-issues-from-antonio` journals and any files under `data/support/`). Extract every error a user or agent hit. Check each against `feat/dev`: fixed (name the commit), still present (reproduce or point at the code), or friction that should change by design. Write the list to `docs/metasmith/plans/` as a short table for the user to review. It feeds tutorial 6 and may spawn fix tasks outside this plan.

Gotchas: a journal describes the code at its date. Verify against current code before calling anything unfixed.

### T4. Registry and project-layer design

Write the design into this plan as a short contract, and stop for approval before building it. The proposed shape:

- An `@op` decorator in `metasmith.ops` records each public op: group, verb, parameter parsers for non-scalar types (`NAME=VALUE`, JSON, `step=k:v`), choices, a hidden marker for callbacks and model objects, and the GUI section and `data-tour` anchor that perform it. The docstring is the help text for both the CLI and Python.
- A project layer in ops addresses SSH hosts, agents, workflows and runs by name inside a project directory, which is the GUI's existing on-disk layout (`gui/store.py`). Path-addressed ops stay. The CLI gains `--project`, and Python gets `metasmith.api` (the registry as plain functions) beside the `Agent` object model used for authoring.

Gotchas: deployed agents call the CLI over SSH (`agents/pool.py`), so the generated spelling must equal today's. Untangle the `agents/pool.py` → ops import cycle before the registry depends on it.

Contract drafted at `docs/metasmith/plans/registry-design.md` (in the worktree). Its decisions, its group-naming question and the migration order govern T7 to T9 once approved.

### T13. Tutorial page machinery

The tutorial page is the source. A Sphinx extension under `docs/metasmith/source/_ext/` adds:

- a `tutorial` directive for the page header: id, summary, prerequisites, next links, rendering the shared header;
- a `step` directive with options for the step id, GUI anchor, done rule and short in-app instruction, holding a `cli` block, a `python` block and the prose;
- synced tabs built on sphinx-design's `tab-set` with one `sync-group`, persisted across pages in localStorage;
- a GUI-port box that rewrites every GUI link;
- build outputs: the joined bash script, the joined Python script (both downloadable), and the in-app tutorial JSON.

The frontend build reads the JSON, so `localPangenome.js` is replaced by its page. Its JS done-predicates stay as named rules in the frontend that steps refer to.

Gotchas: renaming a step id orphans `?tourEdit=1` edits, so the fast lane fails on a removed id that still has a rule. Docs served over https cannot fetch from the http GUI, so the page only links to it. GUI links open in one named window.

### T14. Seekable in-app tutorials

The hash form `#tutorial/<id>/<step>` opens a tutorial at a step. A fast-forward route runs the page's Python script up to that step against the GUI's own project, for real. Tutorial objects have stable names (`tutorial-<id>-agent`, `tutorial-<id>-workflow`) with get-or-create semantics, so a repeat seek reuses the deployed agent and the solved workflow and a rerun hits the cache. A "use your own data" action copies the tutorial's workflow to a new name.

Gotchas: creates reject duplicates, deploy always redoes its work, and runs always get a new name. The project ops used by the scripts need get-or-create forms. A new workflow from the same template re-mints value ids and misses the cache, so fast-forward never recreates the tutorial workflow.

### T15. Test lanes

Three lanes. Only the first runs by default:

- **Fast (unit):** every tutorial page parses, every step's anchor exists in the frontend source, every done rule exists, and the CLI golden snapshot holds. Seconds.
- **`e2e/tutorials` (e2e_virtual):** each tutorial's scripts through the virtual runtime. About a minute.
- **`e2e/hpc` (slow, opt-in):** each tutorial's bash and Python scripts for real on `METASMITH_TEST_HPC_HOST`, with `METASMITH_TEST_HPC_PRESET` and `METASMITH_TEST_HPC_HOME`. Skips when the host is unset. Jobs chain with Slurm dependencies and are polled, never watched from a local loop.

Gotchas: run the HPC lane once per tutorial when it is written and once at the end, never per edit. Move the hard-coded `sockeye` and `chamois` in the agentic scenarios onto the same variables.

### T16. MAMBA runtime

Gotchas: conda solves on login nodes get killed, so setup-env runs inside a job. Use a dedicated agent home.
